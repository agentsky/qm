# Replace static secrets with federated credentials

We run qm on Kubernetes through the Helm chart and want the long-lived secrets out of it. This proposal assumes the earlier one, "One Secret per workload in the Helm chart", has landed. After it, the values are still static, the routing lists are maintained by hand, and the CLI has no Kubernetes target to render them from.

The deploy plane is mostly done. The AWS deploy role is assumed through GitHub OIDC with audience and subject pinned. Image pushes use the per-job token. Images are signed without a stored key. The runtime plane has none of this.

Here is what is left. The CLI declares 41 first-party secret names. Nine are not secret material, so 32 real secrets remain. More live outside that list: `FLY_SANDBOX_API_TOKEN`, `SECURITY_SCREEN_PROXY_TOKEN`, `NPM_TOKEN` in the release workflow, `imagePullSecrets` where images come from a private registry, and two that core requires but the CLI never declares, `MODEL_GATEWAY_API_KEY` and `DEPLOY_APPS_SESSION_SECRET`. Those two are worth declaring whatever happens to the rest. The bar throughout is rotation without a human.

The worst one is `CORE_SIGNING_SECRET`. It is one symmetric HMAC key shared by core and every surface plugin. Any holder can forge any other holder's requests, so a compromised admin container can sign as the portal. The signature carries no caller identity. `verifySignature` checks signature, freshness, and replay only, so core cannot tell which surface is calling. With one key and one value, rotation is a fleet-wide atomic event with no overlap. `PORTAL_IDENTITY_SECRET` has the same shape: the portal signs a user identity, and core and admin verify it. The trusted OIDC entry uses it a third time for a single-use admin assertion, and adds `PORTAL_TRUSTED_OIDC_CLIENT_SECRET`, which the CLI does not declare.

What we would like to build, in order

- Per-surface ServiceAccounts in the chart. It declares one for every workload today. Splitting it comes before any identity work.
- Per-surface identity from projected ServiceAccount tokens. Each surface gets a projected token with `audience: qm-core` and a short expiry that the kubelet rotates, and sends it as a bearer. Core verifies it through `TokenReview`, caches a success no longer than a stated revocation budget, serves from cache only within that budget when the API server is unreachable, and fails closed past it. Offline JWKS verification never overrides a rejection; it is for the STS and Fly issuers below. Core then knows which surface is calling, and nothing is minted or stored by anyone. `PORTAL_IDENTITY_SECRET` goes away: once core knows the calling ServiceAccount, the user claims are a payload that account asserts, and the only question is whether it may. `AUTH_CLIENT_SECRET` goes away too: in the embedded topology the portal mints it at start and hands it to the broker in memory. Two things stay. The trusted-entry admin assertion keeps its purpose binding, its one-minute expiry, and its single-use `jti` in the durable replay store, because authenticating the caller is not the same as consuming a privileged operation. And user identity forwarded through web-ui and admin becomes a short-lived capability that core mints for the portal. It binds the user, the organization, the human impersonator if any, the ServiceAccounts allowed to present it, an expiry, and a `jti`. It carries no operation scope, because the portal proxies requests without parsing them; core authorizes each operation against the user as it does today. It carries a distinct type claim and is signed under a key the egress proxy does not hold, because core's gate treats any token under `CAPABILITY_SECRET` as an agent capability. Intermediaries forward it with their own token and cannot change it. On ECS the same shape runs on STS web identity tokens from each surface's own task role. Fly Machines mint their own OIDC tokens. Docker keeps the HMAC. Bearer mode needs TLS or an encrypted cluster network between surfaces and core, which the chart does not wire today. Every step keeps the HMAC accepted as a fallback until the new path is proven.
- Key rollover for the ten keys that are verified against exactly one value: `CORE_SIGNING_SECRET`, `CAPABILITY_SECRET`, `PORTAL_IDENTITY_SECRET`, `SKILL_SIGNING_SECRET`, `AUTH_TOKEN_SECRET`, `AUTH_CLIENT_SECRET`, `PORTAL_SESSION_SECRET`, `DEPLOY_APPS_SESSION_SECRET`, `AWS_DEPLOY_GATE_SECRET`, and `CONNECTOR_SECRET_KEY`. Rollover has three steps: prepare, activate, retire. Every instance accepts the new key before any producer signs with it. Producers switch only after every consumer holds it. The old key retires only after everything it produced has expired or been re-encrypted, backups included. Accepting the current and previous key is not enough on its own, because a producer that refreshes first signs with a key an unrefreshed verifier does not hold. Without this, rotating any of these keys through External Secrets Operator and a pod restart is an outage. With it, ESO with a refresh interval is a safe carrier for everything that cannot be federated. No refresh interval is set on any of these keys before this lands.
- A `kubernetes` sandbox backend and deploy provider that use core's own ServiceAccount, scoped by RBAC to a sandbox namespace, instead of Porter's admin API. This is the only route that removes the Porter token rather than storing it somewhere else.
- The database credential on both databases we run. On RDS: IAM auth with a `pg` password callback, which version 8.13 supports, and RDS Proxy with end-to-end IAM so the pooled path has no password either. Under CloudNativePG: a rotation Job generates the password and writes it to a Secret, and the operator applies it to the role without coordinating with the pod. Zero-outage rotation therefore uses two login roles with identical grants, switched by the Job in five steps. Prepare: rotate the inactive role's password. Verify: open fresh logins as that role with the new password, one direct and one through the pooler, and retry until both succeed. Activate: write a new credential generation, the active-role name plus a counter, into the Secret the pod mounts as a file the callback reads per connection. Acknowledge: wait until every core replica and the pooled path report the new generation. Retire: only then may the previous role be rotated again.
- The model keys. Anthropic and OpenAI both offer workload identity federation. Core requests a fresh ServiceAccount token per exchange through the TokenRequest API, because a token re-read from the projected file replays its `jti`, and exchanges it for a short-lived bearer at the vendor's token endpoint. The harnesses use it through a core-side proxy on the provider base URL they already honor. `ANTHROPIC_API_KEY` and `OPENAI_API_KEY` are deleted, not stored, because a leftover key outranks federation in the SDK. The `model-anthropic` boot gate accepts the federation configuration instead. The exchange runs in core because the Pi harness sends the key as a raw header rather than through the SDK. The proxy exists because both harnesses take the credential once at start and a bearer expires.
- Image pulls. The kubelet image credential provider with a projected ServiceAccount token, on by default from Kubernetes 1.34, pulls with workload identity from a registry that accepts such tokens. ghcr does not, so images are mirrored into one that does, and `imagePullSecrets` is removed rather than carried. A small provider plugin is the deliverable. A DaemonSet installs it on managed nodes.
- npm trusted publishing instead of `NPM_TOKEN`. The publisher names the calling workflow, so `publish-cli.yml` stays reusable. The `workflow_dispatch` entry point needs its own publisher or goes away, the historical `npm deprecate` step goes away, and the runner's npm must be 11.5.1 or later.

Two things the code does not have yet

- One path that every credential flows through. `SecretSource` carries connector OAuth clients only. Core reads its own secrets from `process.env` in `config.ts` and snapshots them at boot, so a rotated value is invisible until restart. The CLI and core keep two separate secret spec lists with no import between them. Reconciling the lists and giving the shared spec a Helm or ESO emitter comes first. Every phase that removes a secret keeps reading the static value as a fallback and reports when the fallback fires, so it can be removed with evidence.
- A pooled URL that may differ from the direct one. `pooledDatabaseUrl` rejects a pooled URL whose credentials differ from the direct URL. A callback-authenticated URL has no password to compare, so that check changes under any design.

What this does not do

`SLACK_APP_TOKEN`, `SLACK_SIGNING_SECRET`, and a non-SES SMTP password are minted in vendor dashboards with no API to rotate them. For those the ceiling is the durable store plus a `qm doctor` age report. `SLACK_BOT_TOKEN` rotates without a human once qm handles Slack's opt-in token rotation: a refresh token and expiry beside the stored bot token, a refresh loop, and the one-time exchange. An SES SMTP credential rotates through the IAM access key it derives from, user name and password together as one record. The connector OAuth client secrets are better off: core's resolver already falls back to `SecretSource`, so ESO carries them with no code change and a dashboard rotation propagates without a restart. Where the identity provider accepts a PKCE public client, the secret goes away once the token exchange stops requiring one. The OAuth layer also reads `SLACK_OAUTH_CLIENT_SECRET`, `NOTION_OAUTH_CLIENT_SECRET`, `GITHUB_OAUTH_CLIENT_SECRET`, and `X_OAUTH_CLIENT_SECRET`, which the CLI never declares. The portal captures its external `OIDC_CLIENT_SECRET` and `PORTAL_TRUSTED_OIDC_CLIENT_SECRET` at load. The auth broker's mailer and core's invitation mailer capture the Resend key or the SMTP pair at construction. Those consumers need a restart after a rotation until the credential path reaches them. OpenRouter and Resend rotate through their admin APIs, each leaving a root credential in the rotation Job.

Happy to build this. It splits so the undeclared secrets and the npm change land on their own. The npm change is yours to finish, because only your organization can configure the publisher on the package.
