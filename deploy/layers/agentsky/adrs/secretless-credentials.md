# Getting rid of the static secrets

We run qm on Kubernetes through the Helm chart and have been trying to get the long-lived secrets out of it. We got far enough to think the change belongs upstream rather than in our layer, so here is what we found.

The chart's one-Secret-to-every-pod problem is a separate proposal, "One Secret per workload in the Helm chart", that we would send first; this one assumes it has landed and picks up where it stops. The values are still static, the routing lists are still maintained by hand, and the CLI still has no Kubernetes target to render them from.

The deploy plane is otherwise most of the way there: the AWS deploy role is assumed through GitHub OIDC with audience and subject pinned, image pushes use the per-job token, and images are signed keylessly. The runtime plane has none of it.

Counting what is left: the CLI declares 41 first-party secret names, nine of which are not secret material, so 32 real ones. More live outside that list — `FLY_SANDBOX_API_TOKEN`, `SECURITY_SCREEN_PROXY_TOKEN`, `NPM_TOKEN` in the release workflow, `imagePullSecrets` on a private fork, and two that core requires but the CLI has never heard of, `MODEL_GATEWAY_API_KEY` and `DEPLOY_APPS_SESSION_SECRET`. Those two are worth fixing whatever happens to the rest.

The one we care most about is `CORE_SIGNING_SECRET`. It is a single symmetric HMAC key shared by core and every surface plugin. Any holder can forge any other holder's requests, so a compromised admin container can sign as portal. The signature carries no caller identity — `verifySignature` checks signature, freshness and replay and nothing else — so core cannot tell which surface is calling. And with one key and one value, rotation is a fleet-wide atomic event with no overlap window. `PORTAL_IDENTITY_SECRET` has the same shape in the same direction: the portal mints a signed user identity, core and admin verify it. The trusted-entry PoC now uses it a third way — a purpose-bound, single-use, one-minute assertion the portal signs and core verifies before granting admin — and introduces `PORTAL_TRUSTED_OIDC_CLIENT_SECRET`, undeclared by the CLI like the connector client secrets; both fold into the same phases.

What we would like to build

- Per-surface identity from projected ServiceAccount tokens. Each surface gets its own ServiceAccount and a projected token volume with `audience: qm-core` and a short expiry that the kubelet rotates; it sends the token as a bearer and core verifies it through `TokenReview` or the cluster issuer's JWKS. Core learns which surface is calling, nothing is minted or stored by anyone, and `PORTAL_IDENTITY_SECRET` collapses into it — once core knows the calling ServiceAccount, the user claims are a payload that account asserts, and the only question is whether it may. Two things do not collapse with it. The trusted-entry admin assertion keeps its purpose binding, its one-minute expiry, and its single-use `jti` in the durable replay store, because authenticating the caller is not the same as consuming a privileged operation. And user identity forwarded through web-ui and admin becomes a short-lived capability core mints for the portal, bound to the user, the human impersonator if any, the surfaces allowed to present it, and an expiry, signed under a key only core holds; intermediaries forward it with their own token and cannot alter it, and core authorizes each operation against the user as it does today. On ECS the same shape runs on STS-issued web identity tokens from each surface's own task role, verified against the account's STS issuer; Fly Machines mint their own OIDC tokens; Docker keeps the HMAC. Bearer mode needs TLS or an encrypted cluster network between surfaces and core, which the chart does not wire today, and verification through `TokenReview` rather than offline JWKS wherever revocation matters.
- Multi-key verification for the ten keys verified against exactly one value — the HMACs, the cookie keys, `CONNECTOR_SECRET_KEY`. Rollover is prepare, activate, retire: every instance accepts the new key before any producer signs with it, producers switch only once every consumer holds it, and the old key retires only after everything it produced has expired or been re-encrypted, backups included. Current-plus-previous alone is not enough, because a producer that refreshes first signs with a key an unrefreshed verifier does not hold. Without this, rotating any of them through External Secrets Operator plus a reloader is an outage: signature mismatch, every session invalidated, or every connector row undecryptable. With it, ESO with a `refreshInterval` is a safe carrier for everything that cannot be federated, on any cloud.
- A `kubernetes` sandbox backend that talks to the cluster API with core's own ServiceAccount, RBAC-scoped to a sandbox namespace, instead of Porter's admin API. It is the only route that removes the Porter token rather than storing it somewhere nicer.
- The database credential, on both databases we run. On RDS, IAM auth with a `pg` password callback (8.13 supports it) and RDS Proxy so the pooled path is token-authenticated too; the master password stays but rotates itself under `manage_master_user_password`. Under CloudNativePG, the operator owns the application role, rotates it into a Secret the pod mounts as a file the same callback reads per connection, and its `Pooler` runs PgBouncer with an operator-managed auth role. Under CloudNativePG the operator applies a password change with no coordination with the pod, so zero-outage rotation uses two alternating login roles switched by the rotation Job, which verifies fresh direct and pooled logins with the prepared password and waits for every consumer to acknowledge the new generation before the old role becomes eligible again; on RDS, IAM on a role cannot share that role with a proxy password, and RDS Proxy does end-to-end IAM as of September 2025, so the application role has no password anywhere.
- The model keys. Anthropic's and OpenAI's workload identity federation are both GA: core exchanges a freshly minted projected ServiceAccount token for a short-lived bearer at each vendor's token endpoint, the harnesses consume it through a core-side proxy on the provider base URL they already honor, and `ANTHROPIC_API_KEY` and `OPENAI_API_KEY` are deleted rather than stored. The exchange has to run in core because the Pi harness sends the key as a raw header rather than through the SDK, the key has to leave the chart because it outranks federation in the SDK's precedence, and the bearer has to reach the running consumer — both harnesses take the credential once at start, so core fronts the model API with an authenticated proxy that attaches the current bearer per request.
- Image pulls. The kubelet image credential provider with a projected ServiceAccount token (on by default from Kubernetes 1.34) pulls from Zot with workload identity, so `imagePullSecrets` is removable rather than carried. The small provider plugin is the deliverable; a DaemonSet installs it on managed nodes.
- npm trusted publishing instead of `NPM_TOKEN`.

Three things we got wrong on the first pass, which we would rather flag than have you find

- **There is no existing seam to hang this on.** `SecretSource` carries connector OAuth clients only; core reads its own secrets straight from `process.env` in `config.ts`, which also snapshots them at boot so a rotated value is invisible until restart. The CLI and core keep two separate secret spec lists with no import between them, and the CLI has no Kubernetes target, so nothing today can render the chart's per-workload routing lists from the spec. Reconciling those and giving the spec a Helm or ESO emitter comes first.
- **`pooledDatabaseUrl` rejects a pooled URL whose credentials differ from the direct one**, and a callback-authenticated URL has no password to compare, so that check changes under any design.
- **Per-surface ServiceAccounts do not exist yet.** The chart declares one for every workload. Splitting it is step one of the identity work, not a detail.

What this does not do

`SLACK_APP_TOKEN`, `SLACK_SIGNING_SECRET`, and a non-SES SMTP password are minted in vendor dashboards with no API to rotate them; for those the ceiling is the durable store plus a `qm doctor` age report, and `SLACK_SIGNING_SECRET` still needs a stored path. `SLACK_BOT_TOKEN` meets the bar once qm handles Slack's opt-in token rotation — a refresh token and expiry beside the stored bot token, a refresh loop, and the one-time exchange — and an SES SMTP password rotates through the IAM access key it is derived from. The connector OAuth client secrets are better than that: core's resolver already falls back to `SecretSource`, so ESO carries them with no code change and a dashboard rotation propagates without a restart, and where the IdP accepts a PKCE public client the secret goes away entirely once the token exchange stops requiring one. The portal's external `OIDC_CLIENT_SECRET` and `PORTAL_TRUSTED_OIDC_CLIENT_SECRET` take the same carrier but are captured at load, so they need a restart until the seam reaches the portal. The OAuth layer also reads `SLACK_OAUTH_CLIENT_SECRET`, `NOTION_OAUTH_CLIENT_SECRET`, `GITHUB_OAUTH_CLIENT_SECRET`, `X_OAUTH_CLIENT_SECRET`, which the CLI never declares. OpenRouter and Resend rotate through their admin APIs, each leaving a root credential one hop up in the rotation Job. Bedrock is no longer needed for a keyless model call, since federation does that on every cloud.

Happy to build this if you are interested, and happy to split it further so the undeclared secrets and the npm change land independently of the larger refactor. The npm change is yours to finish in any case: trusted publishing names the calling workflow, so `publish-cli.yml` stays reusable, but only your organization can configure the publisher on the package.
